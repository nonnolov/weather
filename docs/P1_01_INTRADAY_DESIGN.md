## Comparison contract

1. Scope by `channel=line`, exact recipient, current location ID, and timezone. Read the most recent **durable accepted rain delivery**, daily or intraday, ordered by `created_at DESC, id DESC`. Recognize explicit daily/intraday rain namespaces; exclude unrelated forecast alerts. Inspect the newest record first: null/unsupported evidence means unknown, not permission to fall back to an older record. LINE acceptance with committed evidence is the baseline; handset receipt is unknown. Neither latest source nor failed/unsent/suppressed candidate replaces it.
2. Normalize evidence/candidate boundaries to UTC; treat naive stored timestamps as UTC. Match exact `(start,end)` pairs, never local hour labels, rank positions, daily maxima, or totals. Each interval remains `(t-1h,t]`. Require valid hourly boundaries, unique interval keys, finite probability 0–100 and nonnegative hourly mm, with both fields present. Missing/invalid values are unknown, never zero.
3. Freeze one decision clock. Future intervals have `start >= now`; exclude elapsed and in-progress intervals, even if their end is future. Do not prorate mm. Require candidate source retrieval strictly newer than baseline source retrieval; source IDs alone establish no novelty. Reject future retrieval timestamps and known model-time regression; null model time is recorded unknown, not proof of freshness or accuracy. Different provider or changed timezone requires a new compatible baseline through an approved delivery path.
4. Define comparison window W as every whole future hourly interval ending within `now + 6h`, whose start belongs to today's location-local date. Require at least two consecutive hours. Require 100% candidate **and frozen baseline** coverage of W, including both metrics. Do not shrink W to hide missing rows. Sparse data outside W does not invalidate this decision, but cannot support statements outside W. P0 v1 covers one local day, so cross-day comparison is deliberately unsupported. Future approved intraday evidence must freeze all available candidate local-day hourly intervals, W, and exact sent text/source. Freezing only W would unnecessarily lose later horizon coverage after baseline advancement. Later comparisons still validate every needed interval; do not alter old JSON or reconstruct evidence from source rows.
5. Recheck current location, newest baseline, source freshness, cooldown, and identities under a recipient/location lock immediately before send. Compare against frozen evidence values, including unselected hours. Apply significance before choosing at most two display periods; display the triggering change among those periods. Existing daily selection/ranking remains untouched. Ranking changes alone have no significance.

Returning to a location may reuse its baseline only if still fresh, timezone/provider-compatible, and fully covered. Other locations/recipients never lend evidence. Same-ID coordinate mutation cannot be detected from legacy evidence, which omits GPS: require location identity stability; known coordinate reassignment invalidates baseline. Invalid timezone skips intraday rather than silently changing scope. Daily timezone fallback stays unchanged.

## Conservative proposed policy values — ALL UNAPPROVED

| Parameter/decision | Proposal | Rationale and tradeoff |
| --- | --- | --- |
| Candidate age | `0 <= now - retrieved_at <= 90 minutes` | Fits a possible hourly refresh with limited delay; does not prove provider/model freshness. Older snapshots skip. |
| Baseline age | Delivery age and frozen source age both `<= 24 hours` | Bounds old comparisons while permitting morning baseline use later that day. Missing overlap still skips; old baseline never auto-refreshes through a send. |
| Horizon/coverage | W above: up to 6h, current local-start day, minimum 2 whole hours, 100% both metrics in both records | Near-term decisions, no invented overlap. Loses late-night/partial-data alerts; intentional first scope. |
| Probability delta | Increase `>= 20 percentage points` on an aligned interval | Absolute points, not relative percent: 50% to 70% is +20 pp, not a 20% increase. Filters small threshold crossings; may miss smaller consequential revisions. |
| Rainfall delta | Increase `>= 5 mm` on an aligned **hourly interval** | No daily-total comparison. Larger revision threshold reduces noise; may miss lower-intensity changes. |
| Escalation | Candidate interval meets existing strong selection AND probability delta or hourly-mm delta passes | Example 70% to 90% qualifies; 69% to 70% alone does not. A fallback-only revision does not trigger this first policy. |
| Newly qualifying rain | Baseline has no strong interval anywhere in W; candidate has strong interval with aligned +20 pp OR +5 mm | Avoids calling rank changes or small crossings new rain. Fallback baseline can become strong. Unknown baseline intervals cannot support absence. |
| Earlier onset | Both records have strong rain in W; candidate earliest strong start is >=2h earlier, starts within next 4h, and aligned baseline at that start is non-strong | Captures meaningful timing shift even without a magnitude delta. Later onset/other shifted windows do not trigger alone; qualifying escalation still may. |
| Cooldown | `now - last durable accepted rain delivery.created_at >= 3h`, same recipient/location, daily or intraday; no exception | Caps interruptions and survives midnight. May miss urgent escalation; any bypass requires separate policy approval. Daily 06:00 is never blocked by intraday cooldown. |
| Weakening/disappearance | No weakening-only message; preserve baseline | Avoids noisy all-clear claims and missing-data ambiguity. Repeated true weakening stays uncommunicated; later escalation compares against last delivered evidence. |

Use inclusive numeric boundaries. Apply quality/scope/source checks, then identity/content suppression, significance, cooldown, final locked recheck. If several triggers pass, send one update with ordered reasons: earlier onset, new rain, escalation. An extra strong window when baseline already has strong rain triggers only aligned escalation or earlier onset; mere selection crossing is insufficient. Daily aggregate change, later shift alone, fallback-only change, and top-two reorder alone suppress. These proposed change rules do not modify existing selection thresholds.

## Dedupe, baseline advancement, and reliability

Keep daily key `rain:{location_id}:{local_date}` intact. Propose separate intraday key `rain-intraday:v1:{location_id}:{event_digest}` within existing delivery uniqueness. Event digest includes baseline delivery ID, policy version, and canonical changed absolute intervals/reasons/values. Include candidate source ID in evidence for traceability and replay checks, **not as the sole event identity**.

Canonical content fingerprint sorts complete absolute intervals and metric values, normalizes numeric representations, includes provider/timezone, and excludes run IDs, retrieval timestamps, daily aggregates, score/rank, and presentation order. Compare candidate against baseline; also check committed intraday evidence for same source or identical content under the same baseline. Different IDs with identical content must suppress. Fingerprint the whole frozen comparison coverage, not only displayed top two. No new evaluation ledger is proposed: suppressed candidates can be reevaluated later; after cooldown they may send if still significant and fresh. Never mark them delivered.

Use a stable recipient/location transaction lock for all future intraday contenders, not just a candidate digest. Daily send would need that additional shared lock without altering its daily identity, so overlapping daily/intraday decisions serialize. After acquiring it, reread committed baseline/cooldown/current location, then freeze evidence before network await. For SQLite tests, explicitly simulate ordered contenders; SQLite success does not validate PostgreSQL locking. Abort/retry if baseline/location changes before the final check. Commit each future accepted intraday delivery promptly rather than accumulating a recipient batch; this is a proposed small transaction boundary, not an outbox redesign.

Only a successful push plus durable committed evidence advances baseline. Flush is insufficient. LINE failure creates no baseline; ambiguous timeout or accepted push followed by flush/commit failure can cause duplicate retry. A unique constraint runs after push and cannot prevent every external duplicate. Lock scope/connection failure can also defeat suppression. **No exactly-once or handset-delivery promise.** Existing daily batch commit has the same push-before-commit gap. Frozen JSON is not DB-enforced write-once; deletion of a location destroys baseline history. Preserve existing evidence verbatim.
